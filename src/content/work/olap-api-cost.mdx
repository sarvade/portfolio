## What was at stake

A creator-facing API was failing at peak traffic in one region. Its success rate had fallen to about 70%, and backend asked for a higher rate limit, which is usually the first fix people reach for.

I ran the numbers before agreeing. Each call was scanning millions of rows in the OLAP cluster behind the API, so a higher limit meant more of those scans per second on the same cluster. The API might have looked better for a while, and the cluster would have taken the hit.

## Diagnosis

I read the query plans with the owner of the OLAP cluster, which runs Apache Doris. The query filtered on a long `IN` list. Once a filter produces more scan keys than the engine allows, it stops using the prefix index to narrow the scan. Nothing errors. The query still returns correct results; it just reads far more data than it needs to.

I look for this kind of bug on purpose: every dashboard is green, the output is right, and the cost is wrong.

## The fix

A one-line query hint got the engine using the prefix index again, and rows scanned per call dropped 40 to 80 times. No schema change, no new hardware, no redesign.

Then I raised serving capacity by about a third, with the before and after numbers attached to the change. At the new limit the cluster does 30 to 60 times less scanning than it did at the old one.

## Three months later

During an infrastructure incident, traffic failed over to a backup environment that didn't have this tuning, and the same API hit its limit. A backend engineer asked me for a quick limit change.

I said no and gave him something he could act on. Raising the cap in an environment without the fix would have repeated the original mistake with less margin. The rule I proposed: measure the real peak over a set window, and file the formal change only if traffic stays above the threshold past the failback ETA. Traffic failed back before it came to that, and nothing unreviewed went into production during the incident.

## Result

The success rate recovered, and the API has stayed under its new limit since. Reviewing scan cost before capacity became the team's default first step for OLAP-backed list APIs. Later, a colleague's new interface failed scan testing days before launch; I walked him through the same plan and hint, it passed on time, and I added the pattern to the team's [AI debugging skill](../ai-oncall-skills/).

The whole fix was one line.

## What broke, and what changed

- **The engine switched plans without telling anyone.** The `IN` list produced more scan keys than the engine allows, so it stopped using the prefix index: same results, 40-80× the work, no error. Checking scan cost before capacity is now the team's first step for OLAP-backed list APIs.
- **The failover environment didn't have the fix.** The backup had none of the tuning, and the same API hit its limit there. A decision rule kept the response measured, and nothing unreviewed shipped.

## What I’d do differently now

- Ship query tuning with the API's configuration, so a failover environment inherits it.
- Alert on rows scanned per call as well as latency and errors. A cost cliff shows up in scan volume before it shows up as failures.
