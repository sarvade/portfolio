## What was at stake

A product-facing API was failing at peak traffic in one region. Its success rate had dropped to about 70%. Backend wanted the rate limit raised, which is the fix everyone reaches for first.

It would have moved the incident somewhere worse. Every call was scanning 8.24 million rows in the OLAP cluster behind it, so more calls meant more load on a shared cluster, not a healthier API.

<Callout label="The call">
  Make each call cheaper before allowing more of them. I owned the query, so the cost was mine to fix.
</Callout>

## Diagnosis

I read the query plans with the owner of the OLAP cluster, which runs Apache Doris. The query filtered on a long `IN` list. Past a certain number of keys, the engine stops using the prefix index to narrow the scan, and nothing errors when that happens. The query just reads far more data than it needs to.

## The fix

A one-line hint capped the number of scan keys, so the engine used the index again. Rows scanned per call dropped by 40 to 80 times.

## Three months later

During an infrastructure incident, traffic failed over to a backup environment that had none of this tuning, and the same API hit its cap at about 250 QPS. A backend engineer asked for a quick patch.

I said no, but I didn't stop at no. I gave him a decision rule: measure the real peak, set a threshold, and file the formal change only if traffic stays above it past the failback ETA. Nothing unreviewed went in during the incident.

## Result

The success rate recovered and the API has run under the new limit since. The approach became the team default for OLAP-backed list APIs, and I reused it to unblock a colleague's new interface that had failed scan testing days before its launch date.

The change itself was small. That's the point: the expensive fix was the wrong one.
