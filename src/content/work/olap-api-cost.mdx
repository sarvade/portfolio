## What was at stake

A creator-facing API was failing at peak traffic in one region, with its success rate down to about 70%. Backend wanted the rate limit raised, which is the fix everyone reaches for first.

The capacity math said otherwise. Every call was scanning 8.24 million rows in the shared OLAP cluster behind it. At the existing 150-QPS cap, that is up to 150 × 8.24M ≈ 1.2 billion rows scanned every second. Raising the cap would not have healed the API. It would have moved the incident into the OLAP cluster itself.

<Callout label="The call">
  Make each call cheaper before allowing more of them. I owned the query, so the cost was mine to fix.
</Callout>

## Diagnosis

I read the query plans with the owner of the OLAP cluster, which runs Apache Doris. The query filtered on a long `IN` list. Past a certain number of scan keys, the engine stops using the prefix index to narrow the scan, and nothing errors when that happens. The query keeps returning correct results while reading far more data than it needs.

That is the class of bug I look for: green dashboards, correct output, wrong cost.

## The fix

A one-line query hint on the scan-key setting (`max_scan_key_num`) put the prefix index back to work. Rows scanned per call dropped 40 to 80 times. No schema change, no new hardware, no redesign.

## Three months later

During an infrastructure incident, traffic failed over to a backup environment that had none of this tuning, and the same API hit its cap at about 250 QPS. A backend engineer asked me for a quick limit change.

I said no, and I didn't stop at no. Raising the cap in an environment without the fix would have repeated the original mistake with the safety margin already gone. So I gave him a decision rule he could forward: measure the real peak over a defined window, and file the formal change only if traffic stays above the threshold past the failback ETA. Traffic failed back before the threshold mattered, and nothing unreviewed went into production during the incident.

## Result

The success rate recovered, and the API has run under the new limit since. Reviewing scan cost before capacity became the team's default first step for OLAP-backed list APIs. I later walked a colleague through the same plan and hint when his new interface failed scan testing days before its launch date; it passed on time, and I added the pattern to the team's [AI debugging skill](../ai-oncall-skills/) so the next person doesn't need either of us.

The change itself was one line. That's the point: the expensive fix was the wrong one.
