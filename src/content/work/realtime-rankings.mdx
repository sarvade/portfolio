## What was at stake

The feature shows creators the top-performing live sessions and products each hour, so they can learn from what is working right now. The original design read the serving database on every request, scanning across millions of rows, and it couldn't meet its latency budget. The feature had stalled, and the effort in flight was tuning the query.

## Diagnosis

Before writing any code, I drew the hour-by-hour data flow on paper (events, windowed aggregation, ranking messages, serving store) and walked it through with the infrastructure owner to check my model against reality. That is where the real constraint showed up.

The query itself was fine. The access pattern was the problem: every page load ran a full scan while a person sat waiting for it, and tuning can only shave so much off a full scan.

<Callout label="The call">
  Stop computing at read time. Do the heavy work once, as events arrive, and make the page read a precomputed answer.
</Callout>

Flink streaming jobs over a live-commerce event stream of more than 1.5 billion events, producing hourly revenue and traffic rankings. The results go through a message queue into a serving store indexed for ranking. A page load now costs the same whether there are a hundred live sessions or a million.

The shape of it, as an illustrative pattern rather than production code:

```sql
-- Flink SQL: hourly aggregates that feed the rankings, computed as events arrive
insert into hourly_rankings
select session_id,
       window_start,
       sum(order_amount) as revenue,
       count(*)          as interactions
from table(
  tumble(table live_events,
         descriptor(event_time),
         interval '1' hour))
group by session_id, window_start, window_end;
```

## Privacy as a pipeline property

The product shows revenue in ranges and participation is opt-in, so creators can compare themselves with each other without anyone's earnings being exposed. I built the pipeline around those two rules from the start, so the privacy comes from the data itself and not only from how the page displays it.

## Result

Rankings return instantly, query time and compute cost dropped by orders of magnitude, and the feature launched for A/B testing.

## What broke, and what changed

The original design did its heavy work at read time. Every request scanned millions of rows, the cost grew with the number of live sessions, and the page missed its latency budget. Precomputing upstream replaced the scan with a lookup.

## What I’d do differently now

- Wire the A/B readout into the pipeline from the first release, so the result is a measured lift and not just a launch date.
