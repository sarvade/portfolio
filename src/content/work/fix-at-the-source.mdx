## What was at stake

The feature marks a creator's best videos so they can learn what to make more of. It disappeared for creators in one region, which made it a P1. Months later, the list of quality videos and the badge on each video started to disagree, and nothing makes a product look less trustworthy than contradicting itself on a creator's own dashboard.

I was the named data owner for the APIs behind it, serving a region I can't query directly.

## Restore first, and say what's left

The outage came from a filter that only looked at a single day's partition, so any creator whose latest partition landed late simply dropped out. I shipped the smallest reversible fix the same day. It introduced duplicate rows for some creators; I said so in the ticket the same day, fixed it, confirmed the sibling API needed no change, and wrote down the risks I knowingly hadn't removed (an unbounded partition scan and a hard-coded floor date) so they were visible debt rather than a trap for the next person.

## Then find the assumption

When the list and the badge disagreed, my first read was that this was a defensible design trade-off. Instead of arguing it, I proved the mechanism (field-by-field access to a restricted upstream table showed specific videos had genuinely been re-scored) and brought the PM a product decision rather than code: should a video keep the badge once it earns it, or be re-evaluated every day? She said keep it. That turned my trade-off into a bug, and I said so in the thread.

The root cause was an assumption nobody had written down. Both APIs were downstream copies of one source table, and that table was built on the belief that a video's quality flag, once set, never flips back. It did flip back, and nothing in the system noticed.

## Fix one: make the source remember

My first design made the source table cumulative: carry forward everything already tagged, add what qualifies today. In a three-day test it recovered 2,993 videos that had silently lost the badge. Then my diff validation against production caught it corrupting 67,565 rows in another region: I had aggregated an attribute that isn't constant per video. I replaced the aggregation with an anti-join, so today's values always win and yesterday's pool only fills in videos missing from today's data, and validated again to 0.0000% difference.

The pattern, illustrative rather than production code:

```sql
-- Cumulative pool: today's fresh values win;
-- yesterday's pool fills in only what today's data lacks
insert overwrite table quality_pool partition (dt = '{{ ds }}')
select t.item_id, t.category_id
from   daily_items t
left join quality_pool p
       on  p.item_id = t.item_id
       and p.dt = '{{ yesterday_ds }}'
where  t.dt = '{{ ds }}'
  -- qualifies today, or already earned it
  and  (t.is_quality = 1 or p.item_id is not null)
union all
select p.item_id, p.category_id
from   quality_pool p
left join daily_items t
       on  t.item_id = p.item_id
       and t.dt = '{{ ds }}'
where  p.dt = '{{ yesterday_ds }}'
  and  t.item_id is null;  -- anti-join: absent today
```

## Fix two: remove the second copy

In review, my tech lead raised two things. A job that reads its own previous output is fragile, since one failed run quietly poisons every run after it. He was right, and I treated it as a hard production gate rather than a detail. He also asked a bigger question: why did two APIs need two stores at all?

I took that question to the team that runs the OLAP store, and backend confirmed that every call to both APIs is scoped to a single creator. That made the simpler design viable. I added the badge flag to the table the list already reads and updated its sync, so the list API returns the badge directly. Two answers can't diverge when they come from one row. My tech lead and I chose this over my validated cumulative job, and the second store is slated for retirement.

While working through the new design I also found that the list table's partition retention caps history at about six months, which quietly turns "the badge never disappears" into "the badge disappears after six months". Catching that in a table definition, rather than in a creator's complaint six months later, is why I read configuration as carefully as code.

## Result

Creators had the feature back within the day. The deeper fix came out of an explicit product decision rather than a guess, and product got a formal heads-up that the badge's behavior was changing, so nobody discovered it from a dashboard. My own validation caught my own bug before any creator saw it, which is the reason I insist on it.

**Status:** the one-table design is agreed and was scheduled with backend; it isn't confirmed live yet, and the six-month retention cap is still open.

## What broke, and what changed

- **A single-day filter made late data look like no data.** Any creator whose latest partition landed late dropped out of the feature. The restore widened the filter to every partition up to the date; deduplication came in the follow-up.
- **My restore introduced duplicate rows.** I disclosed it in the ticket the same day and fixed it. Since then, every “obvious” fix gets a row-count and duplicate check before it ships.
- **My first durable fix aggregated an attribute that isn’t constant per video,** which corrupted 67,565 rows before validation stopped it. I no longer aggregate a column that varies per key; if it varies, it needs a join, not a `MAX`.

## What I’d do differently now

- Ask the product question the moment the spec goes silent. I spent time defending a trade-off that one question settled.
- Before writing code to keep two copies in sync, ask whether the second copy needs to exist.
