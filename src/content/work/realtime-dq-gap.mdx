## What was at stake

Creators were seeing videos in their list with zero revenue and zero views, and leadership wanted to know why. The story everyone had already settled on was a broken filter for a new content type. Several people were treating it as a defect with a fix to find.

If that story was wrong, a fix would ship, nothing would change, and the real problem would end up under a closed ticket.

## Eliminate layer by layer

I started from the number the creator sees and worked backwards one layer at a time, looking for the layer where it changes.

The day's partition was complete, tens of millions of rows, so this wasn't stale data. Whatever was wrong had to be specific to certain items, which ruled out the filter theory.

## Close what isn't a bug, with receipts

For the three items behind the escalation, I read the realtime Flink job. The flag passes straight through from an upstream event stream that another team owns, and it defaults to zero when the event hasn't carried a value yet. That can produce false negatives, so I waited 24 hours to rule out lag and then checked the ground-truth dimension table. All three really were not the content type the ticket assumed. I closed that thread as not-a-bug and attached the evidence.

## Then find the one that is

I scaled the check from 3 items to all 236 that had been flagged, in both pipelines.

That put the gap in the realtime pipeline, specifically in my own realtime transform job and not in the upstream team's stream. The check is simple enough to run before anyone writes a fix. As an illustrative pattern, not production code:

```sql
-- Same items, both pipelines, one expected value
select count(*) as items,
       sum(case when coalesce(o.flag, -1) <> f.expected
                then 1 else 0 end) as offline_wrong,
       sum(case when coalesce(r.flag, -1) <> f.expected
                then 1 else 0 end) as realtime_wrong
from      flagged_items f
left join offline_daily o
       on o.item_id = f.item_id and o.dt = '{{ ds }}'
left join realtime_view r
       on r.item_id = f.item_id;
```

One open question could still change the picture: did the 236 items come from the live product page or from a separate dashboard? If they came from the dashboard, we were investigating the wrong surface, and "fixed" would mean something different. It stays on the list until someone answers it.

## Where it stands

The team stopped chasing a filter fix. The real gap is narrowed to one job, and I set up a working group with the realtime, warehouse and product owners to close it. When it's closed, I'll add the mismatch rate after the fix.

## What broke, and what changed

- **A default can hide missing data.** The realtime job turns a flag the upstream event hasn’t carried yet into a zero, so “not known yet” looks the same as “no”. Any zero in that path needs checking against ground truth, which is what I did. What caused the 19 is still open; a default like this is one way a zero can mislead.
- **The source of the flagged list came up late.** Whether the 236 items came from the live page or a dashboard was only raised partway through. It changes what “fixed” means, so it should be asked first.

## What I’d do differently now

- Confirm where a flagged list came from (the live page or a dashboard) before the first query.
- Write a null when an upstream field hasn’t arrived, not a zero, so missing data shows up as missing.
