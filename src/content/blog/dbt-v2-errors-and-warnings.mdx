Here is a dbt project setting with a typo in it:

```yaml
# dbt_project.yml
models:
  probe:
    +materialised: table
```

On dbt 1.12.6 with the DuckDB adapter, `dbt build` creates every model as a view and finishes with `PASS=1 WARN=0 ERROR=0`. No warning mentions the British spelling. On dbt v2, the same project doesn't get past parsing:

```text
[error] [SerializationError (dbt1013)]: Invalid model definition `probe.+materialised`:
Unrecognized key `probe.+materialised`. Custom keys must go under `+meta`.
```

That is the headline change in dbt v2, which dbt Labs [announced as generally available](https://docs.getdbt.com/blog/dbt-v2-is-ga) on 16 September 2026 (2.0.0 reached PyPI two days earlier). The project is now parsed by a Rust engine against a [tightly defined language spec](https://docs.getdbt.com/blog/dbt-core-v2-is-here), so a whole class of mistakes that v1 tolerated in silence now stops the run. Most upgrade friction will come from these errors, and they are the good kind: each one points at a line, and fixing it makes the project more correct than it was.

The changes worth worrying about are the other kind, the ones that still let the build pass and now do something different, announced by a warning at most. To find out where those are, I ran the same small projects on both versions in this environment and compared what landed in the database. One of them is a masking macro that silently stops masking after a reasonable-looking fix, while dbt v2 reports success and exits 0. This post covers what shipped, how the upgrade changes fall into three groups, what the experiment showed, and the checks I'd add to CI before switching.

## What shipped

The facts first, from dbt Labs' docs and announcements.

- **Two distributions of one engine.** v2 is built on the code of the dbt Fusion engine. In June, dbt Labs [released that runtime under Apache 2.0](https://docs.getdbt.com/blog/dbt-core-v2-is-here) as the next dbt Core. At GA the names changed: [the Fusion engine is now just called dbt, and dbt Core v2 is called dbt OSS](https://docs.getdbt.com/blog/comparing-dbt-and-dbt-oss). `pip install dbt` gives you the first, under the [dbt Product Licensing Agreement](https://www.getdbt.com/licenses-faq); `pip install dbt-oss` gives you the second, under Apache 2.0. dbt Labs recommends the first; it adds local features such as SQL comprehension, linting and LSP support.
- **It is a single binary with no Python runtime.** Adapters use [ADBC drivers instead of Python adapter libraries](https://docs.getdbt.com/docs/dbt-versions/dbt-upgrade/upgrading-to-v2), downloaded from the dbt Labs CDN on first run and cached for offline use after that.
- **Seven adapters, so far.** The [v2 adapter lifecycle table](https://docs.getdbt.com/docs/supported-data-platforms) lists Snowflake, BigQuery, Databricks, Redshift and DuckDB as generally available, Apache Spark as beta and ClickHouse as private beta. Postgres, Trino, Athena and every other v1 adapter are not on it.
- **v1 is still supported.** The upgrade guide says 1.x remains fully supported, but over time new capabilities will land in v2 only. dbt 1.12 can already delegate parsing to the new parser with `--use-v2-parser`, and v1 and v2 can run side by side: the v2 manifest is `v12`, readable by v1, so `state:modified`, `--defer` and docs generation work across a mixed fleet.
- **The pace is quick.** `2.0.0` was uploaded to PyPI on 14 September; by 9 October the [recommended `latest` channel](https://docs.getdbt.com/docs/dbt/dbt-releases) was on 2.0.8, the version I tested.

dbt Labs also provides [dbt-autofix](https://github.com/dbt-labs/dbt-autofix), a tool that rewrites deprecated patterns, and the upgrade guide tells you to clear every deprecation warning before switching.

## Three kinds of upgrade change

The [upgrade guide](https://docs.getdbt.com/docs/dbt-versions/dbt-upgrade/upgrading-to-v2) lists many changes. Sorting them by how you find out about them is more useful than reading them in order. This grouping is mine, not dbt Labs':

1. **Loud.** The project used to run and now fails at parse time: unknown config keys, YAML typos, undefined macros, variables and generic tests, duplicate docs blocks, conflicting package versions, the removed `--models` flag. You can't miss these. CI goes red.
2. **Quiet.** The project still runs, the result can differ, and the signal is a warning or nothing. This group is small, and it is where the risk is.
3. **Operational.** The SQL is the same, but how the run behaves around it has changed: thread counts, where drivers come from, which features need a login, how orchestrators call dbt. Nothing fails at parse; things fail in production, or the job just gets slower or faster.

The point of the grouping is effort allocation. Loud changes take time but carry little risk, because the parser does the finding for you. Quiet changes need a check you build yourself. Operational changes need someone to read the guide with your deployment in mind.

## What I tested

I wanted measured answers for the changes in the second and third groups that could be checked locally, so I ran small purpose-built projects on both versions. This is the setup, and the full method is at the end of the post.

- **Versions:** dbt-core 1.12.6 with dbt-duckdb 1.11.0, against `dbt-oss` 2.0.8 and `dbt` 2.0.8. Each in its own Python 3.13 virtual environment. v2 fetched `libadbc_driver_duckdb-1.5.4` on first run.
- **Machine:** a Linux cloud sandbox with 2 vCPUs and 7 GB of memory.
- **Target:** a local DuckDB file. Only DuckDB, so anything adapter-specific (threads on Snowflake, for example) is out of scope.

The first three rows are the loud kind doing its job. v1.12.6 printed no warning for either typo in my DuckDB runs. dbt's [deprecations reference](https://docs.getdbt.com/reference/deprecations) says some of the related custom-key warnings are raised only on Snowflake, Databricks, BigQuery and Redshift, so a project on one of those may have seen warnings that mine didn't.

Two results differ from what the upgrade guide describes. The guide says the `return('xyz') + 'abc'` pattern returns `'xyz'` in v2 with a warning; in my run the macro produced an empty string. The pattern is rare, and the guide itself calls it uncommon, but it shows that a warning can mean "this value changed", not just "this style is deprecated". The guide also says seeds with trailing commas no longer produce an extra empty column; on DuckDB both versions created one, so I left that row out rather than report a difference I couldn't reproduce.

## The fix that unmasks the column

The rows marked Quiet in the middle of that table are the ones I'd worry about, because they compose into a realistic failure. Start with a masking macro, the kind that lives in a shared package of privacy helpers:

```sql
-- macros/mask.sql, in a package called privacy_utils
{% macro mask_if_pii(col) %}
  {%- if config.get('contains_pii', false) -%} md5({{ col }})
  {%- else -%} {{ col }}
  {%- endif -%}
{% endmacro %}
```

And a model that uses it:

```sql
-- models/users.sql
{{ config(materialized='table', contains_pii=true) }}
select {{ privacy_utils.mask_if_pii('email') }} as email
from {{ ref('raw_users') }}
```

On 1.12.6 this compiles to `md5(email)`. On v2 it fails at parse, because `contains_pii` isn't a dbt config:

```text
[error] [UnusedConfigKey (dbt1060)]: Ignored unexpected key `"contains_pii"`.
```

The fix the error message suggests for the `dbt_project.yml` form, "Custom keys must go under `+meta`", is the right fix for the model. So is what dbt-autofix does. I ran `dbt-autofix deprecations` (version 0.22.6) on this project, and it rewrote the model to `meta={'contains_pii': true}`. When the macro sat in the project's own `macros/` folder, it also rewrote `config.get('contains_pii', false)` to `config.meta_get('contains_pii', false)`, and the result was correct on both versions.

When the macro sat in an installed package, autofix left it alone, because by default it doesn't touch packages (there are `--include-packages` options, but the autofix README notes those edits are reverted at the next `dbt deps`). Now the model says `meta={'contains_pii': true}` and the package still asks `config.get('contains_pii', false)`. [`config.get()` doesn't read `meta`](https://docs.getdbt.com/reference/dbt-jinja-functions/config): it returns the default and warns. So the default wins. Here is what each version did:

This isn't a v2 bug, and it isn't v2-specific: 1.12.6 did exactly the same once the key was under `meta`. What v2 changes is that you can no longer avoid the move. A project that kept custom keys at the top level on 1.x, ignoring deprecation warnings it may not even have been shown, has to move them now, and every macro that reads them has to change in the same step. Some of those macros live in code you don't own. [`config.meta_get()`](https://docs.getdbt.com/reference/dbt-jinja-functions/config) only exists from dbt 1.10, so a package that still supports older versions has a reason not to have switched yet.

### What `--warn-error` does and doesn't stop

The obvious defence is to make warnings fatal. I ran the broken project again with `--warn-error`:

- **dbt 1.12.6:** the warning became a compilation error inside the model, the model failed, `users` was never created, exit code 1.
- **dbt v2.0.8 (both distributions):** the run ended with `Finished 'build' with 1 error`, exit code 1, and `Summary: 2 total | 2 success`. The `users` table existed and contained the unmasked email.

So in v2, at least for this warning in my DuckDB runs, `--warn-error` changes the exit code but not what gets written. That makes it a gate for CI, not a guard for production. If CI builds into a scratch schema and fails the merge, nothing leaks. If the first time the warning fires is a scheduled production run with `--warn-error`, the job goes red after the data is already in the table.

<Callout label="The judgment call">
A privacy macro that defaults to "not sensitive" fails open. Any config drift, a renamed key, a moved key, a package that wasn't updated, turns masking off without an error. For anything security-relevant, use <code>config.meta_require()</code>, which raises when the key is missing, or default to masking and opt columns out. Then a broken lookup costs you a failed build instead of a leak.
</Callout>

## The operational changes

These don't show up in a parse and mostly can't be tested on a laptop, so this section is reading, not measurement, unless I say otherwise.

**Threads mean something different on some warehouses.** In v1, `threads` was how many nodes ran in parallel. In v2, [on Snowflake and Databricks](https://docs.getdbt.com/docs/dbt-versions/dbt-upgrade/upgrading-to-v2) dbt manages parallelism from platform limits and backpressure, and `threads` becomes a cap; on BigQuery and Redshift it is respected, and `0` or no value lets dbt optimize. A profile that set `threads: 32` to be sure is now an upper bound. My reading is that the first runs after an upgrade are when warehouse queueing, concurrency limits and warehouse costs are most likely to move, so watch them.

**Drivers come from a CDN on first run.** That is convenient on a laptop and a problem on a CI runner with no outbound internet or a fresh container per job. In my environment the DuckDB driver landed in `~/.cache/com.getdbt/adbc/`, so that is the directory I'd bake into the image or restore from a CI cache, then confirm by running with the network blocked. The upgrade guide says subsequent runs work offline but doesn't give the cache path, so check it on your own image. The [dbt and dbt OSS comparison post](https://docs.getdbt.com/blog/comparing-dbt-and-dbt-oss) also documents installing an adapter package instead, for example `pip install dbt-snowflake`, which bundles the driver, for networks that block the CDN.

**Strict static analysis depends on which binary you installed.** `static_analysis: baseline`, the default, parses SQL without a warehouse connection and reports findings as warnings. `strict` resolves column types and references for the whole project before anything runs, and it is what column-level lineage needs. The upgrade guide says strict requires `dbt login` and that unauthenticated runs fall back to baseline, while the [licensing FAQ](https://www.getdbt.com/licenses-faq) says every engine feature works without a login. I tested it with a model that selects a misspelled column, `nme` instead of `name`. This one I measured:

- **dbt 2.0.8, not logged in** (`dbt login status` said unauthenticated): strict ran and failed the compile with `No column nme found. Available are probe.main.a.name, probe.main.a.id`, exit code 1.
- **dbt-oss 2.0.8:** strict did not run. The compile succeeded with exit code 0 and one warning: "this distribution of dbt OSS does not include the static analysis engine."
- **Baseline on either:** compiled successfully, no warning about the column.

So the docs disagree with each other and the binary decided. The part that matters is the second bullet: a team that picks dbt OSS for licensing reasons and sets `--static-analysis strict` in CI gets a green check that never ran the check. That belongs with the quiet changes, and `--warn-error` on the CI job catches it.

**Orchestrators that import dbt need checking.** v2 ships a `dbtRunner` with the familiar `invoke()` shape. In the 2.0.8 package source, both distributions raise `NotImplementedError` for the `manifest=` and `callbacks=` arguments ("callbacks= (EventManager hooks) are not yet supported"). Any integration that injects a pre-parsed manifest or listens to dbt events in-process won't work unchanged. The `dbtRunnerResult` docstring in the same file documents exit code `2` for "completed with elevated warnings", which is worth knowing if a wrapper treats anything non-zero as a crash.

**Unit tests run before the rest of the DAG.** The guide says `dbt build` now runs all unit tests first, because v2 knows column names and types without querying the warehouse. In my one probe the operational outcome matched v1: a failing unit test skipped its model and that model's child, and an unrelated branch still built. The log also showed the unit test starting after two unrelated staging models had built, so I wouldn't depend on the order either way.

## Is it faster?

The June announcement promised "significant parse time improvements, especially on the largest dbt projects" without numbers. The [GA post](https://docs.getdbt.com/blog/dbt-v2-is-ga) adds some: projects that took 20 minutes to parse finishing in under one, and the author's 10,000-node benchmark project compiling in 17 seconds instead of 70. Those are dbt Labs' figures. I measured `dbt parse` on generated projects of my own: every model after the first 20 joins two random earlier models, and each model has two data tests (`not_null` and `unique` on `id`), a model description and one column description. Five runs per configuration, median wall time, including process start-up.

A cold v2 parse beat a full v1 parse at every size, by about 5x at 500 models and 3x at 5,000. In seconds the saving grows with the project; as a ratio it shrank in my runs.

The comparison that matters for day-to-day work is different, though. v1 has had partial parsing for years: when nothing changed since the last run, it reloads the saved manifest instead of parsing. Against that, v2 was faster at 500 models and slower at 2,000 and 5,000. Running dbt-oss a second time with `target/` left in place was no faster than the first run (slower at 500 models, slightly faster at 5,000), and v2 doesn't support the `--partial-parse` flags in job runs.

So in this environment v2 was much faster exactly where v1 is slow (CI jobs on fresh checkouts, any change that invalidates partial parsing, first runs) and not faster on the edit-and-rerun loop where v1 already had a cache. Treat this as one machine and one synthetic project shape. Real projects with heavy macros, many packages or large YAML files could land differently in either direction, and v1's partial parse after a real edit, which I didn't time, probably sits somewhere between its two columns.

## A pre-upgrade checklist

1. **Get to 1.12 and clear every deprecation warning.** The upgrade guide requires clearing every deprecation warning first, and dbt Labs' announcement posts recommend moving to 1.12 before switching. Then run `dbt parse --use-v2-parser` on 1.12; it uses the v2 parser without changing anything else. On the typo project above it reported both errors, so it is a cheap first pass.
2. **Run dbt-autofix, and read its diff.** It is a good tool and it did the right thing in my project. Its scope is your project's files.
3. **Grep what autofix didn't touch.** Search `dbt_packages/` for `config.get(` and `config.require(` with keys that aren't dbt configs, and check each against your `meta` keys. The warning text, "was detected as a custom config under 'meta'", is also worth searching for in your logs. Fix those by upgrading the package, or by overriding the macro in your project.
4. **Make warnings fatal in CI, not only in production.** `--warn-error` or `warn_error_options` in the job that builds a pull request into a scratch schema. Production is too late, as the experiment showed. This also catches strict analysis being skipped on dbt OSS.
5. **Diff the output, not just the exit code.** Build the same commit with v1 and v2 into two schemas and compare the tables row by row. A passing build tells you the project is valid; only a diff tells you the data is the same. I wrote up the method in [Totals lie. Diff the rows.](../totals-lie-diff-the-rows/)
6. **Pin the version and the channel.** Move from 2.0.x to 2.0.y deliberately, given how often it ships. The releases page already marks one patch release, 2.0.7, as known bad.
7. **Watch the first week of warehouse metrics** after the switch, because of the threading change.

The loud part of this upgrade will take the most hours and carry the least risk, because the parser is now strict about the things it never checked before. Spend the saved attention on the small set of changes that still pass: anything that reads config through Jinja, anything that turns warnings into errors, and the output tables themselves.

## How to reproduce

Every probe is a few files. The setup:

```shell
python3 -m venv v1 && v1/bin/pip install dbt-core==1.12.6 dbt-duckdb==1.11.0
python3 -m venv v2 && v2/bin/pip install dbt-oss==2.0.8
python3 -m venv v2p && v2p/bin/pip install dbt==2.0.8
python3 -m venv af && af/bin/pip install dbt-autofix==0.22.6
```

Each probe project has a three-line `dbt_project.yml` (name, version, profile) and a DuckDB `profiles.yml` next to it pointing at a local file, used with `DBT_PROFILES_DIR=.`. For the masking case, put the `mask_if_pii` macro in a local package (`packages.yml` with `- local: ../pkg`), run `dbt deps`, commit, run `dbt-autofix deprecations`, then `dbt build` and `dbt build --warn-error` on each version, deleting the database file between runs. Read the result with DuckDB directly: `select * from users`.

For the parse benchmark, a short Python script writes N models, model `i` selecting from two randomly chosen earlier models (seeded), plus one `schema.yml` with `not_null` and `unique` on each model's `id`. Each timing is `dbt parse` as a subprocess. For the cold cases `target/` is deleted before every run; for v1 full parse the flag is `--no-partial-parse`; for v1 no-change the manifest is primed once and the project is left untouched.
